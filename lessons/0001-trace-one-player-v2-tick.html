Player Controller V2 · Lesson 1 · 8 minutes

Trace one motor tick

The controller becomes much easier to change once you stop seeing it as one movement script. It is a pipeline with a deliberate seam between gameplay decisions and KCC mechanics.

Tangible win: after this lesson, you can name the first file to inspect for any movement symptom.

The central design idea

PlayerLocomotionMachine decides what movement should mean. PlayerControllerV2 translates between that decision and KinematicCharacterMotor, which resolves actual motion against the world.

Maintenance rule: change gameplay rules in the machine; change Unity/KCC translation in the adapter. Crossing that boundary without a reason is how controllers become hard to simplify.

A tick, in order

  1. Input events are cached

    InputReader raises move/jump events. The adapter stores continuous move input, a one-shot jump request, and held state.

    Input boundary

  2. KCC begins its update

    BeforeCharacterUpdate converts raw input into camera-relative world direction exactly once for this motor step.

    Adapter

  3. Rotation is proposed

    UpdateRotation projects direction onto the character-up plane and exponentially smooths facing.

    Adapter

  4. Intent meets observation

    UpdateVelocity builds PlayerIntent, observes grounding/velocity from KCC, then calls locomotion.Step(...).

    Seam

  5. Policy emits an output

    The machine resolves mode, buffered/coyote jumps, abilities, tuning, modifiers, gravity, and pending requests into one LocomotionOutput.

    Pure policy

  6. The adapter applies it

    Grounded motion is tangent-projected and smoothed; airborne motion gets acceleration, gravity, drag, and jump influence.

    Motor mechanics

  7. One-shots finish

    AfterCharacterUpdate applies queued teleports and finally consumes jumpQueued.

    Adapter

  8. Presentation reads results

    PlayerAnimationPresenter.Update maps presentation state to animator booleans and emits jump particles once for each new jumped snapshot.

    Presentation

The one-shot jump is deliberately retained until after KCC finishes the step. Unity's Input System invokes action callbacks during input updates; V2 then bridges that event timing into KCC's motor lifecycle. See the official InputAction API and the bundled KCC callback contract.

Two-minute trace

Imagine the player presses Jump 0.05 seconds after walking off a ledge. Predict the path before revealing it in code:

JumpEvent
→ jumpQueued = true
→ PlayerIntent.JumpPressed = true
→ observation is Airborne
→ coyote > 0
→ baseJump = true
→ output.HasJumpInfluence = true
→ motor.ForceUnground()
→ vertical velocity is replaced

Now open PlayerLocomotionMachine.cs and find the exact branch. The important insight is that coyote time is a policy decision; ForceUnground and velocity replacement are motor application.

Retrieval check

A designer asks you to shorten the coyote-time window. Which layer should you change first?

Keep beside the debugger

Open the printable Player V2 layer map. For a bug, walk left-to-right through its debugging order and stop at the first value that is wrong.

Primary reading

Read only UpdateVelocity in PlayerControllerV2.cs, then only Step in PlayerLocomotionMachine.cs. Your goal is not line-by-line recall; it is recognizing the adapter → policy → adapter handoff.

Ask your teaching agent any follow-up question—even “why is this line on this side of the seam?” The next lesson should be chosen from what remains unclear after this trace.

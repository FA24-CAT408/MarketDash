Background — from game scenes to a testing campus

Scope. This explains commit ef90fb0 relative to 4532a1e. The repository also has a very large uncommitted working-tree change; it is deliberately excluded.

Beginner primer (safe to skip): A Unity scene is a serialized collection of GameObjects and components. Loading scenes additively keeps the current scene alive while adding another. An assembly definition (.asmdef) creates a compile boundary: runtime code can ship in a player, editor code runs only inside Unity, and test code can depend on both without leaking NUnit into the game.

Before this commit, CrazyMarket had production menus and level scenes but no purpose-built place to exercise movement, cameras, lighting, NPC interaction, UI, and cross-system behavior in isolation. The change adds 76 files: seven generated scenes, twelve materials, a small runtime framework, editor generation/validation/build tooling, and six EditMode tests.

Intuition — a campus of plug-in laboratories

Think of the core scene as a campus reception desk and each additive scene as a laboratory. The desk knows laboratories by a stable TestZoneId, not by their internal fixtures. A laboratory advertises optional capabilities through interfaces.

Spawn lookup follows the same defensive pattern: request a named spawn, then fall back to Default. Falling below killPlaneY teleports the player to the last successful zone/spawn; if that no longer resolves, recovery falls back to the hub.

Code walkthrough — responsibilities, not file order

1. Contracts keep fixtures decoupled

Assets/TestCampus/Runtime/TestCampusContracts.cs defines seven zone identifiers plus three narrow extension seams: ITestResettable, ITestPresetProvider, and ITestDiagnosticsProvider. A fixture implements only what it supports; the controller never needs fixture-specific types. TestResettableTransform demonstrates the pattern by capturing transform/activity state and clearing Rigidbody velocities during reset.

2. The root owns a zone; the controller owns the campus

TestZoneRoot discovers providers below itself, captures initial state, resolves named/default spawns, and registers on enable. TestCampusController maintains a Dictionary<TestZoneId, TestZoneRoot>, rejects duplicate live identifiers, loads specialist scenes additively, routes resets and presets, teleports the player, and performs kill-plane recovery.

zone scene enabled
  → TestZoneRoot.RefreshProviders()
  → TestCampusController.RegisterZone(root)
  → dictionary enforces one live root per TestZoneId
Lifecycle subtlety: a zone can enable before the core controller exists. The controller's Start waits one frame, scans existing roots, then loads defaults. The editor bootstrap also opens Core additively when Play Mode begins from a specialist scene. Together these handle either scene arriving first.

3. Generation turns conventions into reproducible assets

TestCampusSceneGenerator.BuildAll creates materials, seven scenes, fixtures, spawns, and build-settings entries. The core receives production player/manager prefabs when available; specialist scenes receive focused graybox geometry. This makes the campus reproducible, though the committed scenes remain the executable artifacts developers open.

4. Validation enforces scene ownership

TestCampusValidator.Validate opens every generated scene and checks that each exists, has exactly one uniquely identified root, and contains labeling. Specialist scenes must not own a controller, EventSystem, or CinemachineBrain; Core must own exactly one brain and at least one Cinemachine camera. This prevents duplicated persistent services when scenes are combined additively.

5. Development content stays out of release builds

TestCampusBuildProcessor snapshots EditorBuildSettings.scenes. For a non-development build it temporarily removes paths under Assets/TestCampus/Scenes, then restores the original array after the build. Development builds keep the campus. This changes build input, not the checked-in settings file.

Failure mode: restoration is implemented only in postprocess. The code does not show a try/finally path for a build that aborts before postprocessing, so the artifact should not claim restoration is guaranteed on every failure path.

6. Tests cover the framework seams

TestCampusControllerTests checks registration, duplicate rejection, reset isolation, default-spawn fallback, preset routing, and generated-scene ownership. These are EditMode tests: they validate orchestration and asset structure, not full player movement, camera feel, performance, or every production-prefab interaction.

Behavior change, invariants, and compatibility

BeforeAfter
No dedicated multi-system test environmentOne hub plus six additive specialist zones
Testing depended on production scenes and ad hoc setupGenerator produces repeatable graybox fixtures and materials
No shared reset/preset/diagnostic seamFixture capabilities compose through small interfaces
No structural guard for additive ownershipValidator and EditMode test enforce the scene contract
Only production scenes in build settingsCampus scenes are enabled for development, filtered for release

Key invariants: one active controller, one root per zone ID, one shared camera brain/EventSystem in Core, specialist scenes free of shared-service ownership, named spawn fallback to Default, and reset scoped through the requested root.

Compatibility: production prefabs are reused rather than reimplemented. If a production prefab is absent during regeneration, several generator calls tolerate null and omit it; that makes generation resilient but may yield a less representative campus. The control panel uses legacy runtime UnityEngine.UI.Text, while the validator in this commit merely requires labels and does not yet reject legacy text. The tests establish framework behavior but do not prove a player controller tolerates direct transform teleportation.
